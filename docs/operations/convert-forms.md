# Convert form integration and protected state

Task 9 exposes `RegisterPage(converts:, photos:, congregations:, onSaved:, onCancel:)` and `EditPage(initial:, converts:, photos:, congregations:, onSaved:, onCancel:)`. Supply the same production SupabaseGateway to ConvertRepository and PhotoRepository; pass authorized active congregations from the root's complete traversal. No fake repository, fallback data, environment setup, persistent cache, public URL or signed URL exists in these widgets. `onSaved` receives only the minimal server ID. Registration success can start a fresh empty form.

Task 19 must invalidate the shared boundary synchronously on logout, user switch or scope loss and **unmount every old RegisterPage/EditPage and its ConvertForm**, using a key based on the protected generation. Reusing an old state with a new initial record, gateway, repositories or congregation scope is unsupported. Controller lifetime context additionally prevents a retained payload from being retried under a new boundary. Its `clear()` invalidates pending completions and releases retained payload/signature/operation state; the page calls it on dispose. Root must replace the page immediately in its invalidation callback, rather than wait for network revalidation.

Protected owners that must disappear together:

- ConvertForm owns six text controllers (name, address, landmark, phone, age, date), congregation/gender/worship selections, selected original photo bytes, removal intent, validation/error state and pending picker/submit closures. Dispose clears and disposes all controllers and drops selected bytes. The immutable ConvertDraft snapshot and upload request may remain in an in-flight Future until completion; stale results cannot publish or send a subsequent convert command.
- RegisterPage (also used by EditPage) owns the initial ConvertRecord, authenticated old-photo bytes, photo loading/error state, success state and ConvertSaveController. In-flight metadata/download completions check context immediately before publication.
- ConvertSaveController owns the form lifetime context, convert ID, canonical draft signature (including an in-memory base64 photo signature), immutable editable command payload and operation UUID. It clears on successful logical actions or disposal; unchanged failed commands keep the same operation and payload, including the already uploaded pending asset. A failed upload leaves no convert command and a user retry creates a fresh upload draft/path through PhotoRepository.
- Flutter Image.memory/ImageCache may retain decoded bytes after widget disposal. Root must evict all memory/live image entries during the same invalidation callback and configure bounded caching as in data-gateway.md. No private bytes are persisted.

Photo removal only sets local intent and sends a null `photo_asset_id` when the user saves. Existing downloaded photo stays visible during replacement/removal until successful edit; selection cancellation changes nothing. Old photo URL fields are never loaded. Attached images are fetched with PhotoRepository.get/download through authenticated Storage.

## Android picker and resume integration requirement

The actual SessionRouter.didChangeAppLifecycleState(resumed) calls refresh(), whose first action invalidates protected state and clears feature owners. Android gallery/camera can cause this lifecycle transition before ImagePicker completes. The current safe form captures the context before opening the picker and discards a completion from an invalidated generation. Task 19 must coordinate resume revalidation and picker lifecycle without accepting stale data or weakening logout/user-switch/grant-loss invalidation. Real gallery selection usability after same-user scope revalidation must be verified on a device, alongside logout/user-switch during picker/upload/download. No device or live OAuth/Storage service result is claimed by synthetic widget fixtures. Actual private Storage HTTP enforcement remains a mandatory release prerequisite under the accepted native PostgreSQL profile.
