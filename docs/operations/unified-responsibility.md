# Unified Supabase and static-host responsibility

Planning baseline: Supabase Free for Auth/PostgreSQL/Storage and a separate static web host (Cloudflare Pages Free is proposed in `docs/operations/release.md`). No remote resources were provisioned for this document. Provider limits can change and must be rechecked before release. The application XLSX export is not a backend backup.

## Shared responsibility matrix

| Area | Supabase / static-host provider | Application / repository | Operator responsibility and evidence |
|---|---|---|---|

## Current boundary and evidence

The local final report records 240 passing Flutter tests, 13 native PostgreSQL scenarios including independent-session races, clean `flutter analyze`, web build plus 42-file preflight and debug APK build. It explicitly does not claim live Google OAuth, Supabase Storage HTTP, hosted callback/route refresh, signed Android release or physical-device behavior. The present document does not rerun broad suites and does not create or change provider resources.

The supabase CLI/Docker path was environmentally unavailable during prior verification; the exact migrations ran in the native PostgreSQL harness with synthetic Auth/Storage contracts. This is evidence for SQL behavior, not hosted Supabase service enforcement. Cloudflare Pages is a proposed static host, not an existing deployment. The VM/serverless/function deployment triad is **not applicable** to this plan: the accepted design uses Supabase-managed services and static hosting, with no adopted VM, serverless function, Edge Function or Cloudflare Worker. Reassess only if architecture changes.

## Release and handoff checks

The later gate plan owns an explicit command/evidence record. Before release, operators must verify real provider Auth/Storage access, exact OAuth redirects, hosted direct-route refresh and static asset MIME, signed APK certificate/install and device workflows, workload/quota headroom, encrypted DB plus Storage backup and a restore rehearsal. Each remains open until dated evidence is attached. Do not claim an availability guarantee from a Free plan.

For the future `ieadpe_promote_convert_to_student` handoff RPC, the linked journey plan supplies the Entry/Process/Exit boundary:

1. **Entry:** validate authenticated UID, operation UUID/payload shape, allowed fields, selected `convert_id`, congregation and optional explicitly reviewed in-scope `student_id`; reject missing assignment, revoked grants, malformed/altered retry payload and soft-deleted converts. Actor scope and record scope must be checked server-side.
2. **Process:** acquire actor/scope and record locks in documented order; verify grant and lifecycle; replay matching receipt idempotently; reject operation-ID reuse with altered payload; create or link exactly one student under a unique nullable `convert_id`; write only declared provenance-labelled name/phone/address snapshots; return minimal IDs/status. No enrollment, history rewrite, name-only merge, out-of-scope candidate disclosure, or silent post-link sync.
3. **Exit:** return the minimal authorized response and durable receipt; on failure, leave no partial link and preserve the caller's operation ID/draft for retry. Validate receipt replay/lost response, both competing commit orders, same-scope explicit existing-student selection, out-of-scope denial, revoked grant, terminal/archived behavior and direct RLS/referral projection denial in tests.

The actual migration and test owner is Plan 3, task 2: `supabase/migrations/202610140015_convert_student_link.sql`, `supabase/tests/database/convert_student_link_test.sql`, and `test/database/convert_student_race_test.dart`. The sequence and product policy are Plan 3, task 1 (`docs/integration/handoff-contract.md` and `docs/integration/handoff-sequence.md`). This document records prerequisites; it does not claim the RPC exists.
