### Canonical person identity and legacy mapping

**Plan-confirmed requirement:** one canonical identity/contact source; a student academic extension is created or reused automatically at enrollment; an explicit, unique link is required; never merge by name; unresolved legacy rows remain preserved and reviewable. Enrollment and effective follow-up changes are atomic. The non-new-convert path must not invent conversion fields or a convert event.

**Plan-selected default (P1/P2):** introduce a neutral person record as the canonical name/contact/address owner, with at most one optional convert-specific profile and at most one optional student academic extension per person. Keep student/class/enrollment IDs and academic history stable. Link only by reviewed stable IDs or explicit in-scope operator match; never merge by name or merge across congregation scope. Unmatched and ambiguous legacy rows stay preserved and unlinked for review. Current `convert_id`/snapshot becomes compatibility lineage and is not an editable identity source. New convert registration creates person + convert profile/event; non-new-convert registration creates person without a convert profile; enrollment creates/reuses the academic extension. Shared field edits update the canonical person once; academic and convert-specific answers/events remain with their owners. Existing records require a reviewed forward migration; this is a target contract, not current schema or hosted fact.

All current wrappers are authenticated `SECURITY DEFINER` functions; callers supply neither actor nor authority. Mutation JSON is strict-key validated. ### Deterministic legacy identity transition

Backfill one person per existing `converts` row with a non-null `congregation_id`, including soft-deleted rows; retain the convert UUID and all events. Backfill a `ministry_students.person_id` only when its existing `convert_id` names exactly one convert in the same congregation and the person has no other student extension. Firebase student IDs, Base44 IDs, contact names, normalized-name matches, phone matches, and snapshots are not cross-source identity keys. Students with no valid explicit local `convert_id`, scope mismatch, or duplicate link keep their original row, UUID, name/contact snapshot, enrollment/attendance history, and null `person_id`; no name-only or cross-scope merge occurs. `legacy_firebase_id` remains on the source-owned Ministry row and `converts.legacy_base44_id` remains on the convert row. ### Replay, revision and typed-client rules

Every mutation uses one caller-generated `operation_id` UUID per logical submit, reused unchanged after timeout/retry. Exact same actor, RPC command and payload hash replays the stored success result; changed command/payload under that operation ID emits `operation_conflict`. Authorization and scope checks precede receipt disclosure. Person, convert and student creates use stable caller IDs where listed; convert create returns its server-created IDs in the receipt. Updates require every affected row's `expected_revision`; success increments each changed row once, and no stale write is merged client-side. Cross-row registration, person/student linking, enrollment, and contact/access grant or revoke are atomic. Access writes retain the global advisory/email/UID lock order and increment `private.access_versions` for affected UIDs. Receipt hashing follows the current local PostgreSQL `jsonb::text` SHA-256 contract; no TTL is introduced.

Typed target models: `MinistryPerson(id,congregationId,name,normalizedName,phone,birthDate,address,revision,createdAt,updatedAt,updatedBy)` and `MinistryPersonDraft(name,phone,birthDate,address)` live in `lib/features/ministry/domain/ministry_models.dart`. `Student` carries `personId?`, its own `revision`, and `personRevision?`; canonical identity fields are projected from a `MinistryPerson`. `ConvertRecord` in `lib/domain/models.dart` carries required display `name`, optional `LegacyConvertIdentity(name,phone,address)` only when unlinked, `personId?`, `convertRevision`, and `personRevision?`; the Ministry `ConvertProfile` carries the same separate revisions plus convert-specific fields. `MinistryDirectoryEntry` in `lib/features/ministry/data/ministry_codec.dart` carries `revision`, nullable `email`, and `userAccessId?` (always null for non-global readers); detail reads map to `MinistryContact(email,userAccessId,revision)`. `TeamAccessAssignment(id,userEmail,role,congregationId,boundUserId?)` remains a separate authority model. `PersonRegistrationResult` carries `personId`, optional `convertId`/`studentId`, `personRevision`, and optional `convertRevision`/`studentRevision`.
